# 고전지혜(古典知慧) 개발일지 — 사서오경·사기 RAG 상담 서비스 구축기

> 사서오경과 사기 전문을 웹에서 크롤링하고, 유저의 고민에 고전 지혜로 답하는 Discord 상담 봇을 만들기까지의 전 과정을 기록합니다. 시행착오가 많았던 만큼, 같은 길을 걷는 분들에게 도움이 되길 바랍니다.

## 1. 기획: "옛 사람도 이런 고민 했을까?"

시작은 단순했다. 사서오경(四書五經) 원문과 번역문을 마크다운으로 모으자는 것이었다. 그러다 한 걸음 더 나아갔다 — **이 고전들이 그냥 파일로만 있으면 뭐하나? 유저가 고민을 말하면, 비슷한 고민을 겪은 옛 인물의 이야기를 찾아주면 어떨까?**

"사업이 안 돼서 막막해요" → 《서경》 요전(堯典)의 요임금 이야기
"친구와 싸워서 속상해요" → 《시경》 목과(木瓜)의 영원한 우정

이런 연결을 자동으로 만들어주는 서비스. 이름은 **고전지혜(古典知慧)**.

### 목표 아키텍처

```
[유저 Discord 메시지]
       ↓
[Hermes 게이트웨이] → channel_prompt로 고전지혜 상담사 프롬프트 주입
       ↓
[에이전트] → RAG API 호출 (curl)
       ↓
[RAG 서비스 v4] → ONNX INT8 임베딩 → FAISS 검색 → SQLite에서 청크 로드
       ↓
[에이전트] → 검색 결과 바탕으로 고전 지혜 응답 생성
       ↓
[Discord 채널에 응답 전송]
```

### 기술 스택

| 구성 | 선택 | 이유 |
|------|------|------|
| 원문 출처 | 위키문헌 (ko/zh) | 무료, 텍스트 품질 양호, API 제공 |
| 임베딩 | paraphrase-multilingual-MiniLM-L12-v2 | 다국어 지원, 가벼운 모델 |
| 벡터 검색 | FAISS (CPU) | 경량, 로컬 실행 가능 |
| 청크 저장 | SQLite | 메모리 절약, 온디맨드 로드 |
| 서비스 | FastAPI + uvicorn | 가벼움, 빠른 시작 |
| 서비스 관리 | systemd (user) | 자동 재시작, 서버 재부팅 시 복구 |
| 봇 프레임워크 | Hermes Agent | Discord/Telegram 멀티플랫폼, 채널별 프롬프트 |

## 2. 데이터 수집: 위키문헌 크롤링

### 한국어 번역문 — ko.wikisource.org

한국어 위키문헌에는 `번역:` 네임스페이스(번호 114)에 번역문이 있다. 일반 검색으로는 안 나오니 이 네임스페이스를 직접 탐색해야 했다.

```python
# MediaWiki API로 번역 네임스페이스 검색
params = {
    "action": "query",
    "list": "allpages",
    "apnamespace": 114,  # 번역: 네임스페이스
    "aplimit": "max",
    "format": "json"
}
```

**결과**: 논어 3편, 맹자 2편, 시경 3편, 서경 5편의 한국어 번역 확보. 하지만 대학·중용·역경·예기·춘추는 한국어 번역이 위키문헌에 없었다.

### 한문 원문 — zh.wikisource.org

한문 원문은 비교적 풍부했다. MediaWiki API로 하위 페이지를 타고 내려가며 전문 수집.

| 책 | 원문 | 한국어 번역 |
|---|---|---|
| 논어 | 20편 (166KB) | 3편 (15KB) |
| 맹자 | 전문 (284KB) | 2편 (32KB) |
| 대학 | 예기/대학 (7KB) | X |
| 중용 | 예기/중용 (14KB) | X |
| 시경 | 50편 (49KB) | 3편 (21KB) |
| 서경 | 50편 (104KB) | 5편 (30KB) |
| 역경 | 64괘+계사전 (101KB) | X |
| 예기 | 50편 (385KB) | X |
| 춘추 | 춘추좌씨전 (1.5MB) | X |
| 사기 | 전 136권 (2.2MB) | X |

### 크롤링 시행착오

**1. Rate limiting (429 Too Many Requests)**

zh.wikisource.org는 API 호출에 매우 민감하다. 처음에는 딜레이 없이 호출했다가 429 에러가 쏟아졌다. 6~7초 간격으로 줄여야 정상 작동.

```python
import time
time.sleep(7)  # zh.wikisource는 6~7초 필수
```

**2. 대학·중용은 독립 페이지가 없다**

처음에 대학과 중용을 독립 책으로 검색했는데, zh.wikisource에서는 예기(禮記)의 하위 장(章)으로 수록되어 있었다. 예기/대학, 예기/중용 경로로 접근해야 함.

**3. 춘추는 좌씨전(左氏傳)이 핵심**

춘추 경문 자체는 짧지만, 실제 내용은 춘추좌씨전에 있다. 하위 링크 4개를 찾아 각각 크롤링해야 전문 확보 가능. 531,727자 분량.

**4. 사기(史記) — 136권의 대규모 크롤링**

사기는 본기(本紀)·표(表)·서(書)·세가(世家)·열전(列傳) 등 136개 하위 페이지로 구성. 각 페이지를 순회하며 크롤링. 최종 799,859자 확보.

### 위키문헌 메타데이터 제거

크롤링 직후에는 위키문헌의 편집 링크, 분류 태그, 각주 등이 섞여 있었다. 정규식으로 일괄 제거:

```python
# 위키문헌 메타데이터 제거
patterns = [
    r'\[편집\]',           # 편집 링크
    r'\[\[분류:.*?\]\]',   # 분류 태그
    r'\[\[파일:.*?\]\]',   # 파일 링크
    r'==\s*각주\s*==.*',   # 각주 섹션 이하 전부
]
```

최종 14개 마크다운 파일 정리 완료.

## 3. RAG 서비스 설계 및 구현

### 청킹(Chunking) 전략

고전 텍스트는 특성이 다르다:
- **논어/맹자**: 대화 단위로 자연스럽게 분리
- **시경**: 시(詩) 편 단위
- **서경**: 장(章) 단위
- **역경**: 괘(卦) 단위
- **사기**: 열전 인물 단위

통일된 청킹 규칙:
- 최대 500자, 오버랩 50자
- `##` 헤더로 장 구분되면 거기서 분리
- 메타데이터: `{book, chapter, language, text}`

```python
def chunk_markdown(text, book_name, max_chars=500, overlap=50):
    """마크다운 텍스트를 청크로 분할"""
    sections = re.split(r'\n(?=#)', text)
    chunks = []
    for section in sections:
        if len(section) <= max_chars:
            chunks.append(section)
        else:
            # 슬라이딩 윈도우로 분할
            for i in range(0, len(section), max_chars - overlap):
                chunks.append(section[i:i + max_chars])
    return chunks
```

**결과**: 4,503개 청크 생성 (한국어 86개, 한문 4,417개)

### v1: sentence-transformers + FAISS (초기 구현)

처음에는 가장 익숙한 조합으로 구현:

```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")
embeddings = model.encode(chunks)
# FAISS 인덱스 구축
index = faiss.IndexFlatIP(dim)
index.add(embeddings)
```

**문제**: 메모리. PyTorch를 통째로 올리니 RAG 서비스만 **RSS 759MB + Swap 233MB = 총 990MB**. 서버 전체 RAM이 2GB인데 절반을 잡아먹는다.

### v2: 2단계 검색 + 한국어 부스트

한국어 번역 청크가 86개뿐이라 검색에서 한문 청크에 묻히는 문제가 있었다. 2단계 검색 도입:

1. **1단계**: 한국어 청크 86개에서만 검색 → 스코어 1.3x 부스트
2. **2단계**: 전체 4,503개 청크에서 보충 검색

**검색 품질 개선 효과**:

| 쿼리 | v1 스코어 | v2 스코어 | 개선율 |
|------|-----------|-----------|--------|
| "사업이 안돼서 막막해요" | 0.693 (zh) | 0.894 (ko) | +29% |
| "외로워" | 0.635 | 0.960 | +51% |
| "리더십" | 0.636 | 0.998 | +57% |

하지만 메모리 문제는 해결 안 됨.

### v3: ONNX Runtime 전환 (1차 메모리 최적화)

PyTorch를 제거하고 ONNX Runtime으로 교체하기로 결정.

**ONNX 내보내기**:

```python
from optimum.onnxruntime import ORTModelForFeatureExtraction
model = ORTModelForFeatureExtraction.from_pretrained(
    "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2",
    export=True
)
model.save_pretrained("~/gojon-wisdom/onnx_model/")
```

모델 크기: 448MB (safetensors) → 448MB (ONNX FP32). 크기는 같지만 PyTorch 런타임 없이 실행 가능.

**INT8 양자화**:

```python
from optimum.onnxruntime import ORTQuantizer
from optimum.onnxruntime.configuration import QuantizationConfig

quantizer = ORTQuantizer.from_pretrained("~/gojon-wisdom/onnx_model/")
qconfig = QuantizationConfig(is_static=False, approach="dynamic")
quantizer.quantize(save_dir="~/gojon-wisdom/onnx_model_int8/", quantization_config=qconfig)
```

**결과**: 448MB → **112MB** (75% 축소)

**시행착오**:
- `fastembed` 라이브러리를 먼저 시도했다. fastembed는 내부적으로 ONNX를 사용하므로 편리해 보였으나, **런타임 메모리가 720MB**로 여전히 높았다. 패키지 오버헤드가 크다.
- `optimum`의 양자화 API가 버전마다 시그니처가 달라서 `QuantizationConfig(approach="dynamic")` → `is_static=False, approach="dynamic"` 등 파라미터 조정이 필요했다.
- 양자화된 모델로 인덱스를 새로 구축해야 함 (임베딩 벡터가 달라짐). 기존 FAISS 인덱스 재사용 불가.

### v4: SQLite 청크 저장 (2차 메모리 최적화)

v3에서 임베딩 엔진은 경량화했지만, Python 프로세스 자체가 545MB를 차지. 프로파일링 결과:

| 구성 | 메모리 |
|------|--------|
| ONNX 모델 | ~112MB |
| Python 힙 + 객체 | ~352MB |
| 청크 JSON 전체 적재 | ~6.6MB |
| 기타 | ~75MB |

Python 힙 352MB 중 상당 부분이 청크 텍스트 전체를 메모리에 올린 것과 Python 객체 오버헤드. 청크를 SQLite로 마이그레이션:

```python
# JSON → SQLite 변환
conn = sqlite3.connect("gojon.db")
conn.execute("""
    CREATE TABLE chunks (
        id INTEGER PRIMARY KEY,
        book TEXT,
        chapter TEXT,
        language TEXT,
        text TEXT
    )
""")
```

검색 시 FAISS에서 인덱스만 받고, 텍스트는 SQLite에서 온디맨드 로드:

```python
def search(query, top_k=5):
    q_embedding = encode(query)
    scores, indices = index.search(q_embedding, top_k)
    results = []
    for score, idx in zip(scores[0], indices[0]):
        row = db.execute(
            "SELECT book, chapter, language, text FROM chunks WHERE id=?",
            (int(idx),)
        ).fetchone()
        results.append({
            "book": row[0],
            "chapter": row[1],
            "language": row[2],
            "text": row[3],
            "score": float(score)
        })
    return results
```

**최종 메모리**:

| 버전 | RSS | Swap | 총계 |
|------|-----|------|------|
| v2 (PyTorch) | 759MB | 233MB | **990MB** |
| v3 (fastembed) | 720MB | 0 | 720MB |
| v3 (ONNX 직접) | 545MB | 0 | 545MB |
| **v4 (ONNX + SQLite)** | **518MB** | **0** | **518MB** |

48% 절감. Swap 0으로 서버 안정성 대폭 개선.

### ONNX 임베딩 직접 구현

fastembed를 거치지 않고 onnxruntime + tokenizers만 사용:

```python
import onnxruntime as ort
from tokenizers import Tokenizer

session = ort.InferenceSession(
    "model_quantized.onnx",
    providers=["CPUExecutionProvider"],
    sess_options=ort.SessionOptions()
)
sess_options.enable_mem_pattern = False      # 메모리 패턴 비활성화
sess_options.enable_cpu_mem_arena = False    # CPU 메모리 아레나 비활성화

tokenizer = Tokenizer.from_file("tokenizer.json")

def encode(text: str) -> np.ndarray:
    encoded = tokenizer.encode(text)
    input_ids = np.array([encoded.ids], dtype=np.int64)
    attention_mask = np.array([encoded.attention_mask], dtype=np.int64)
    outputs = session.run(None, {
        "input_ids": input_ids,
        "attention_mask": attention_mask
    })
    # CLS 토큰 풀링 + 정규화
    embedding = outputs[0][:, 0, :]
    embedding = embedding / np.linalg.norm(embedding, axis=1, keepdims=True)
    return embedding
```

## 4. Discord 연동 — 시행착오의 연속

### Hermes 게이트웨이 설정

Hermes Agent는 채널별 프롬프트를 설정할 수 있다. 고전지혜 전용 채널 `#🧩-내-문제-꺼내기` (ID: 1508540396505006260) 설정:

```yaml
discord:
  auto_thread: true
  free_response_channels: 1508540396505006260
  channel_prompts:
    '1508540396505006260': |
      당신은 사서삼경과 동양 고전 지혜를 바탕으로 상담하는 고전지혜 상담사입니다.
      [동작 지침]
      1. 사용자의 문제를 분석합니다.
      2. RAG 검색을 수행합니다...
```

### 문제 1: "Unknown Channel" 404 에러

게이트웨이 로그에 수없이 반복되는 에러:

```
discord.errors.NotFound: 404 Not Found (error code: 10003): Unknown Channel
```

원인: `auto_thread: true` 설정으로 봇이 스레드를 만들어 응답하려 했는데, Discord 스레드가 정상 생성되지 않거나 이미 삭제된 스레드에 응답을 보내려 함. 게이트웨이 셧다운 시에도 이 채널에 알림을 보내려다 404.

**해결**: `auto_thread: false`로 변경. 채널에 직접 응답.

```yaml
discord:
  auto_thread: false
```

### 문제 2: 에이전트가 RAG를 무시한다

초기 channel_prompt는 RAG API 호출에 대한 명시적 지시가 부족했다. 에이전트가 일반 지식으로만 답변하고 RAG 검색을 건너뜀.

**해결**: channel_prompt에 **반드시 curl로 RAG API를 호출하라**는 지침을 명시:

```
[동작 지침]
2. 반드시 터미널 도구를 사용해 RAG 검색을 수행합니다:
   curl -s -X POST http://127.0.0.1:18901/search \
     -H "Content-Type: application/json" \
     -d '{"query": "사용자문제핵심키워드", "top_k": 5}'
   - 검색 쿼리는 사용자 문제를 핵심 키워드 2~3개로 요약할 것
   - 반드시 이 API를 호출한 후 결과를 바탕으로 답변할 것

[핵심 규칙]
- 반드시 RAG 검색 API를 호출할 것. 검색 없이 일반 지식으로만 답변 금지
```

**교훈**: LLM 에이전트는 프롬프트에 "도구를 사용하라"고 해도, 구체적인 호출 방법과 예시가 없으면 자체 지식으로 답변하려는 경향이 강하다. API 엔드포인트, 요청 형식, 호출 강제 규칙을 모두 명시해야 함.

### 문제 3: 봇 메시지는 inbound로 안 잡힌다

테스트를 위해 봇 토큰으로 메시지를 보냈는데, 게이트웨이가 이를 유저 메시지로 인식하지 않음. Discord에서 봇 자신이 보낸 메시지는 `on_message` 이벤트에서 필터링되는 것이 정상 동작.

**해결**: CLI `hermes chat -q`로 직접 테스트.

## 8. 교훈 & 회고

### "된다고 끝이 아니다"

초기 구현은 빠르게 됐다. sentence-transformers + FAISS면 30분이면 RAG 서비스 완성. 하지만 **2GB RAM 서버에서 PyTorch가 1GB를 잡아먹으면 나머지 서비스들이 위태로워진다.** "작동한다"와 "운영 가능하다"는 다르다.

### ONNX 전환은 만만치 않다

PyTorch → ONNX는 이론적으로 간단하지만:
1. **양자화 API가 버전마다 다름** — optimum 버전에 따라 `QuantizationConfig` 시그니처가 달라서 문서만 보고는 해결이 안 됨
2. **인덱스 재구축 필수** — 임베딩 벡터값이 달라지므로 기존 FAISS 인덱스 재사용 불가
3. **fastembed의 숨은 비용** — 편리하지만 런타임 메모리가 720MB. 결국 onnxruntime + tokenizers를 직접 써야 진짜 경량화

### 프롬프트에 "도구 써라"만 쓰면 안 된다

LLM 에이전트는 구체적인 API 엔드포인트, 요청 형식, 강제 규칙이 없으면 자체 지식으로 답변하려 한다. `curl -X POST http://127.0.0.1:18901/search -d '{"query":"..."}'` 와 같이 호출 가능한 형태로 프롬프트에 적어야 실제로 호출함.

### Discord 스레드 ≠ 일반 채널

`auto_thread: true`는 포럼 채널에서는 유용하지만, 일반 텍스트 채널에서는 스레드 관리 복잡도만 증가. 삭제된 스레드에 응답하려다 404 에러가 무한 반복될 수 있음.

### 한국어 번역 청크가 적으면 검색 품질이 떨어진다

86개 한국어 청크 vs 4,417개 한문 청크. 벡터 검색은 임베딩 공간의 밀도에 영향을 받으므로, 한국어 청크에 부스트를 주지 않으면 한문 청크에 묻힌다. 2단계 검색 + 1.3x 부스트로 해결했지만, 근본적으로는 한국어 번역을 더 많이 확보하는 것이 최선.

## 9. 향후 개선 방향

1. **한국어 번역 확보**: ko.wikisource에 없는 대학·중용·역경 등의 한국어 번역을 다른 출처에서 보완

4. **응답 속도**: 현재 76초 → 프롬프트 최적화, 검색 결과 캐싱으로 단축
